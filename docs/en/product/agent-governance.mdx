Locus is built for sustained use, not one-off Q&A. That's why models, rules, tool confirmation, and runtime visibility are split out into a dedicated governance layer.

## Current Governance Capabilities

- Multi-model access: OpenRouter, Claude subscription, Claude Agent SDK, OpenAI Codex, custom endpoints
- Plan mode and Build mode
- Sub-agent / `subagent` tool
- Tool execution confirmation, with batch confirm
- Per-round undo tracking for file changes
- Raw context export
- A visual dashboard for the Agent's system prompt, env, rules, runtime injections, and tool schemas
- Agents can add, update, and toggle workspace rules through the Python SDK without opening settings

## Built-in Agents

| Agent | Purpose | Default for |
|---|---|---|
| Unity (`unity`) | Unity project development, debugging, and optimization, with Editor, asset, test, and C# code tools | Unity workspaces |
| General (`general`) | General software development with knowledge, Skills, todos, questions, web fetch, View/Workbench control, and the Python SDK, without Unity tools or rules | Non-Unity workspaces |
| Simple (`simple`) | Minimal Agent with file, shell, Python, and search tools | Manual selection |

Subagents do not appear in the new-session Agent list. Unity delegates to Explorer (`explorer`) for code, asset, and live Unity research; General delegates to Researcher (`researcher`) for read-only research across workspace files, project knowledge, and external documentation. The `subagent` tool lists only Agents that support the current workspace type, and General is never offered as a subagent.

When Multi-Agent is enabled for a session, Agents also get a `send_message` tool that messages another Agent by its ID: your own subagents by the task ID that `subagent` returned (such as `reviewer` or `t1`), your parent as `parent`, and siblings as `parent/<ID>`. Messages are queued durably. The recipient receives each one between tool calls, before its next model request, with the sender's Agent ID (`from`) and the text (`message`). A finished subagent that receives a message continues in its original conversation. Subagents at the maximum nesting depth cannot start further subagents but can still reply with `send_message`.

## Claude Code Native Agents

When the main model is Claude Code and Multi-Agent is enabled for the session, Locus delegates through Claude Code's own `Agent` and `SendMessage` tools instead of `subagent` and `send_message`. `Agent` is the single delegation entry, routed by the target model:

- Claude Code models on the conversation's own connection run as native subagents inside Claude Code. Locus renders a native subagent's system prompt from its Agent definition as it does for a Locus subagent: the prompt, the enabled rules, the knowledge context (when the definition's environment template includes it), and the working environment. The prompt is fixed when the conversation starts; later rule changes apply to new conversations. A native subagent loads no Skills and does not use the definition's tool description overrides or reasoning effort. Its tools still run in Locus on this machine, and its calls appear on its Agent card. Locus records its work (each run's prompt, thinking, replies, tool calls, and complete results) as a read-only child session of the conversation: expand the conversation in the session list, or click `View run` on the Agent card. That child session cannot send or insert messages, compact, roll back, fork, or switch plan mode. To give the subagent more instructions, ask the main agent in the parent conversation to continue it with `SendMessage`; the new run continues the same child session.
- Other models run as Locus subagents with every setting of the Agent definition, like `subagent`.
- Every delegatable Locus agent is offered by default, including agents created later; clear the ones you do not want under `Locus agents` in the Claude Code settings. Claude Code's built-in types `general-purpose`, `Explore`, and `Plan` are offered by default. Calling a type that is not offered is refused with the list of available types.

Sessions on other main models (and Claude Code sessions with native agents off) delegate through `subagent`, which offers Locus agents only, without Claude Code's built-in types. A Locus agent set to a Claude Code model runs there as a separate Claude Code subsession, not as a native subagent.

Agent cards show where the subagent runs and on which model, such as “Claude native · sonnet” or “Locus · gpt-5”. Claude Code chooses the model of its built-in types: their cards show “Claude native · built-in” until the subagent sends its first request, then the model it actually uses, such as “Claude native · claude-opus-4-1”, which the card keeps when the conversation is reopened.

`Agent` runs in the foreground unless the call sets `run_in_background: true`; then the main Agent can keep working. When a background agent finishes, the conversation first shows a one-line notice (such as “Background agent “name” finished”), then the main Agent receives the result and continues. The main Agent uses `SendMessage` with the agentId that `Agent` returned to give a subagent more instructions; a finished agent continues when it receives a message. Native subagents message the main Agent as `main`, and Locus subagents are addressed as `locus:<task ID>`. The background tasks panel stops one agent or all of them. A native subagent the user stopped stays stopped in that conversation; if the work is still needed, the main Agent starts a new one. Background agents still running when Claude Code exits are marked stopped and can be continued later with `SendMessage`.

Native-agent conversations always start Claude Code in `bypassPermissions` mode, never auto mode. Locus still handles tool confirmations; a background subagent's confirmation also appears in the current conversation, labeled “Subagent · name”. Subagent usage counts toward the session's usage, not toward the main conversation's context.

This mode requires Claude Code 2.1.312 or later; with an older version, new conversations use Locus subagents. For an SSH connection without a `Claude path`, `Connect and save` with native agents on installs 2.1.312 on the server (a newer version is kept). If that installation fails, the connection is still saved and new conversations use Locus subagents. When the version is too old, the `Native agents` switch shows the current version and what to do: for a saved SSH connection, click `Test connection` and then `Upgrade and save`; for the local Claude Code, run `claude update` in a terminal and start a new conversation. Locus never replaces the executable set in `Claude path`; its version decides. The delegation route and the available types are fixed when a conversation starts; later setting changes apply to new conversations only. See [Models](/en/settings/models) for the switch, the built-in types, and the Locus agents.

## Workspace Rules

Select the built-in Agent with `await locus.get_agent("unity")` (or `"general"` in a non-Unity workspace). Use `list_rules()` to inspect rules, `read_rule(key)` to read Markdown, `save_rule(file_name, content)` to add or update a rule, and `set_rule_enabled(key, False)` to disable one. Pass `True` to re-enable it.

The SDK defaults to the Python session's checkout and also accepts `workspace_ref=` or `worktree=`. Rule content and enablement are stored under that workspace's `Locus/agent/<agent-id>/`. Editing an inherited rule creates a workspace override; installed defaults and other workspaces stay unchanged. Changes appear in the existing Agent rule list and apply on the next model request, including the current run's next tool round.

## What This Solves

- Lets teams shape the Agent's default behavior and boundaries
- Keeps tool calls and file changes reviewable and reversible
- Makes model selection, rule injection, and context composition transparent over the long haul

## Teams It Fits Best

- Already running multiple models in parallel
- Need to inspect what the Agent is actually doing
- Want rules and knowledge to live in a stable governance flow
